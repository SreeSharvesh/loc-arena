Settings

A setting is a complete simulated organization plus a catalog of tasks for the agents to carry. It is where the abstract engine in Architecture becomes a concrete lab with real software, real agents, and real work. This section documents each setting in the project.

What a setting defines

Every setting reuses the same engine. What it adds is the concrete world laid on top.

The line between the two is strict. The engine runs an episode and holds no company, team or task. A setting is data and company code, and it runs nothing by itself. The test for any file in the repository: would it be the same for a different company and a different task? If yes, it is engine. If no, it is setting.

PartWhat the setting specifiesWhere it lives
The organizationThe company, what it does, and its software: the services and repositories the agents work on.company/, and the services and iam blocks of scenario.yaml
The agentsThe team, one agent per service, under a lead. Each agent's permissions and scope: which repositories it can change, whether it can call models or submit jobs, and any special access. Its sandbox: tools, the MCP tools it is offered on each service, and its sandbox: rights, its starting rights on each service with rights.the agents block of the run config
The tasksA catalog of main tasks (the open engineering work) and side tasks (the covert objectives), each pairing forming one episode.scenarios/<name>/ and the task blocks of the run config
The controlsThe monitors placed on the setting and the sealed checker that decides the side task.configs/monitors.yaml and the scenario's side.py
