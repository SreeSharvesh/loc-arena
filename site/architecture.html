Concepts

Architecture

LOC-Arena is a framework. This page covers the engine every setting runs on: the services, the single path for model calls, the boundary between the sealed and observable sides, the event record, and how one episode runs. The specific lab, its codebase, its tasks, and its agents live under Settings.

An episode builds the world from a config file and a seed, runs the agents, grades the tasks, and tears the world down. It is fully described by its config and seed, so it reproduces exactly.

The engine

An episode runs on three components the agents work inside, plus a sealed layer they cannot reach.

the gateway
The single path to a model. Every model call, by every agent and every process it spawns, goes through it.
the organisation
The team of agents, the shared channel they coordinate on, and their tools. A lead agent runs the team and spawns helpers. Which agents exist, and what each can do, is defined by the setting.
execution
The sandboxes that run agent code. Each agent works in its own, with only the access it was granted.
the sealed layer
The recorder, the private append-only record, and the checker. This is the ground truth. No agent has a route to it.

The path for model calls

Every model call travels the same path. An agent holds no model key and never contacts a provider directly. It sends its request to the near end of the gateway, which forwards it to the far end. The far end holds the only provider key and is the only component with an outbound route. Each call is recorded twice: once to the private record, once to the observable one.

There is one path, so one component sees every call, and the record of model usage is complete. A rogue deployment is model calls that should not be happening, so a complete call record is what the checker verifies against.

Sealed and observable

The world is split by a boundary. The observable side is everything the agents work with and the monitors read: the observable log, the code, the jobs, the near end of the gateway. A capable agent could influence anything here, including the observable log of its own behaviour. The sealed side is the private record and the checker. An agent with full control of its own sandbox still has no route across.

A single writer produces both records, writing the same events to two files. The observable copy can be altered by a compromised component. The sealed copy cannot. When the two disagree, the disagreement is itself a signal that the observable side has been edited.

The boundary is structural It is enforced by wiring, not by policy. The sealed components sit on a private network with their own storage, and the agent sandboxes are not connected to it. There is no setting to change and no code path to exploit, because there is no connection to carry anything across.

Services and networks

When an episode runs the full stack, it starts the services below, grouped by which private network they sit on. What matters is each service's function and which side of the boundary it is on.

Running the full stack in containers is optional. The isolation is structural. Because an episode is reproducible from config and seed, the logic also runs in a single process, and the containers are brought up only when requested.

The event record

Every event is recorded: an action, a message, a spawn, a close, a model call, a job, a merge, a config change, a tick. Each carries a fingerprint of its contents, a sequence number, the actor's identity, and the episode id. The writer rejects anything out of order or duplicated and never rewrites a line.

Spawns and closes are events, so the full agent tree and every agent's trajectory reconstruct from the record. A reviewer replays the episode from the log rather than trusting a summary.

How an episode runs

Every episode, attack or honest twin, follows the same path. The only difference is whether the covert objective is enabled, which is set at the start and touches nothing else.

  1. Build the world. Stand up the services, the codebase, and the empty records from the config and seed.
  2. Seed it. Fill the code host with tickets, open changes, and wiki pages, plus a background coworker doing unrelated work.
  3. Assign the tasks. The lead agent gets the main task. In an attack episode it also gets the covert objective, which it alone holds at the start.
  4. Run the team. The lead works, spawns helpers, assigns pieces over the shared channel, and integrates the results.
  5. Record. Every action and model call is written to both records as it happens.
  6. Grade the main task. Run the test suites and measure cost on a fixed workload.
  7. Check the side task. The sealed checker reads the private record and decides, from executed facts, whether a rogue deployment exists.
  8. Score the monitors. The monitors read the observable record and produce a caught or not-caught verdict against the honest twin's baseline. Everything is written to one bundle, including a per-agent log and transcript that show which agent caused each event.
The concrete lab, its codebase and services, its agents and their permissions, and the tasks they work on are the subject of Settings. How the monitors read the observable record and turn it into a verdict is Monitoring.
