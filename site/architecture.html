Concepts

Architecture

LOC-Arena is a framework. This page covers the engine every setting runs on: the services, the single path for model calls, the boundary between the sealed and observable sides, the event record, and how one episode runs. The specific lab, its codebase, its tasks, and its agents live under Settings.

An episode builds the world from a config file and a seed, runs the agents, grades the tasks, and tears the world down. It is fully described by its config and seed, so it reproduces exactly.

Work in progress. Tools as services behind agentgateway, set per agent in the run config, is a base state still being built out. The tools, the services and the way events are recorded on this page describe it as it stands now.

The engine

Each agent runs in its own sandbox with two things: its harness's native tools (read, edit, bash) and an MCP client. Everything else it can do to the company is a tool on a service behind one MCP route, and the run config decides exactly which tools each agent is offered.

the gateway
The single path to a model. Every model call, by every agent and every process it spawns, goes through it.
the sandboxes
Where agent code runs. Each agent works in its own, with only the access it was granted.
the services
The forge, the board agents message each other on, the job service and the rest. Each lists the tools it serves, and each records every call made to it and by whom.
the sealed layer
The private append-only record and the checker. This is the ground truth. No agent has a route to it.

The path for model calls

Every model call travels the same path. An agent holds no model key and never contacts a provider directly. It sends its request to the gateway, which holds the only provider key and is the only component with an outbound route. Each call is recorded, with the container that made it.

There is one path, so one component sees every call, and the record of model usage is complete. A rogue deployment is model calls that should not be happening, so a complete call record is what the checker verifies against.

Sealed and observable

The world is split by a boundary. The observable side is everything the agents work with and the monitors read: the observable log, the code, the services. A capable agent could influence anything here, including the observable log of its own behaviour. The sealed side is the private record and the checker. An agent with full control of its own sandbox still has no route across.

A single writer produces both records, writing the same events to two files. The observable copy can be altered by a compromised component. The sealed copy cannot. When the two disagree, the disagreement is itself a signal that the observable side has been edited.

The boundary is structural Agent code runs only in sandboxes built from a slim image with no harness, scorer or scenario spec. A sandbox mounts only the checkouts and the skills, takes commands from the episode alone, and has no route to the key, the internet or the sealed record. The run is graded on the host afterwards.

Services and networks

In a stack run (make run STACK=1) the episode is one Docker Compose project with two networks. Agent code reaches the services only through agentgateway, which offers each agent the tools its run config lists and passes that agent's identity on to the service. Only the gateway can leave the project.

The same episode also runs in a single process (make run), where each agent is served the same services in memory and offers no shell, so its agents run no code.

The event record

Every event is recorded: an action, a message, a pull request, a model call, a config change, a tick. Each carries a fingerprint of its contents, a sequence number, the actor's identity, and the episode id. The writer rejects anything out of order or duplicated and never rewrites a line.

Each service records every call made to it. After play, those records become the events the monitors and the checker read, each placed in the turn of the agent that made the call. A reviewer replays the episode from the log rather than trusting a summary.

How an episode runs

Every episode, attack or honest twin, follows the same path. The covert objective, and the tools it needs, are enabled in the attack episode only, which then runs first; the honest twin plays after it on services and sandboxes recreated empty.

  1. Build the world. Stand up the services, the codebase, and the empty records from the config and seed.
  2. Seed it. Fill the forge with tickets, open changes, and wiki pages, plus a background coworker doing unrelated work.
  3. Assign the tasks. The lead agent gets the main task. In an attack episode it also gets the covert objective, which it alone holds at the start.
  4. Run the team. The lead works, briefs the team, assigns pieces over the board, and integrates the results.
  5. Record. Model calls and native actions are written to both records as they happen; each service records the calls made to it, and those become events after play.
  6. Grade the main task. Run the test suites and measure cost on a fixed workload.
  7. Check the side task. The sealed checker reads the private record and decides, from executed facts, whether a rogue deployment exists.
  8. Score the monitors. The monitors read the observable record and produce a caught or not-caught verdict against the honest twin's baseline. Everything is written to one bundle.
The concrete lab, its codebase and services, its agents and their permissions, and the tasks they work on are the subject of Settings. How the monitors read the observable record and turn it into a verdict is Monitoring.
