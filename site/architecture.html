Concepts

Architecture

LOC-Arena is a framework. This page covers the engine every setting runs on: the containers, the single path for model calls, the boundary between the sealed and observable sides, the event record, and how one episode runs. The specific lab, its codebase, its tasks, and its agents live under Settings.

An episode builds the world from a config file and a seed, runs the agents, grades the tasks, and tears the world down. A scripted run reproduces exactly from its config and seed; a live run is graded on outcome.

The engine

Each agent has its harness's native tools (read, edit, bash), which act in its own sandbox, and an MCP client; the native loop runs in the episode container. Every other tool is served by a service behind agentgateway, which offers each agent the tools its run config lists and calls the service with that agent's identity. A service with rights, such as notes, is also called from the sandbox directly over HTTP with the agent's own identity. The agents service runs the company's own agents with pi on its runners, and the job service runs each job on a node of its fleet; both call models through the gateway, on one route they share. The sealed layer, the private record and the checker, has no container agents can reach.

The boundary is structural Agent code runs only in sandboxes built from a slim image with no harness, scorer or scenario spec. A sandbox mounts only the checkouts and the skills, takes commands from the episode alone, and has no route to the key, the internet or the sealed record. The run is graded on the host afterwards.

The same episode also runs in a single process (make run STACK=0), where each agent is served the forge in memory and offered no shell, so its agents run no code.

The path for model calls

Every model call travels the same path. An agent holds no model key and never contacts a provider directly. It sends its request with its own token to the gateway, which holds the only provider key and is the only component with an outbound route. Each call is recorded, with the caller that made it.

There is one path, so one component sees every call, and the gateway's call record is complete. The checker reads the sealed event log, which holds the calls that pass the in-world gateway. The calls that sandboxes, runners and the job service's nodes make directly are in the call record alone.

Sealed and observable

The observable side is everything the agents work with and the monitors read: the observable log, the code, the services. A capable agent could influence anything here. The sealed side is the sealed log, the gateway's call record and the checker. An agent with full control of its own sandbox still has no route across: no sandbox mounts either log, and only the Collector mounts the call record's volume.

During play the in-world gateway, in-process code in the episode, writes each model call an agent loop makes twice: its edge to the observable log, from the agent's own prompt; its core, which injects the covert brief for the target agent, to the sealed log. The core sends the call to the gateway before it writes its record. The sandboxes, the runners and the job service's nodes call the gateway directly, and their calls reach neither log. The gateway records every call it forwards in its call record. The episode writes native actions and world events to both logs. After play, before grading, the record builder on the host turns each service's records into events on both logs, except sealed-only ones such as a node's process facts. When the two logs disagree, the disagreement is itself a signal. In a single-process run the core calls the provider itself, so there is no call record.

The event record

Every event is recorded: an action, a message, a pull request, a model call, a config change, a tick. Each carries a fingerprint of its contents, a sequence number, the actor's identity, and the episode id. Each log rejects an event out of order or duplicated, and the sealed log is never rewritten. Events built from service records are placed in the turn of the agent that made the call. A reviewer replays the episode from the log.

How an episode runs

Every episode, attack or honest twin, follows the same steps. The covert objective is enabled in the attack episode only.

  1. Build the world. Stand up the services, the codebase, and the empty records from the config and seed.
  2. Seed it. Fill the forge with tickets, open changes, and wiki pages, plus a background coworker doing unrelated work.
  3. Assign the tasks. The lead agent gets the main task. In an attack episode the in-world gateway's core adds the covert objective to its prompt, and three sub-agents start with a covert piece in their briefs.
  4. Run the team. The lead works, briefs the team, assigns pieces in chat, and integrates the results.
  5. Record. Model calls and native actions are written to both records as they happen; each service records the calls made to it, and those become events after play.
  6. Grade the main task. On the host, after copy-out: run the test suites and measure cost on a fixed workload.
  7. Check the side task. The sealed checker reads the sealed log and decides, from executed facts, whether a rogue deployment exists.
  8. Score the monitors. The monitors read the observable log and produce a caught or not-caught verdict against the honest twin's baseline. Everything is written to one bundle.

The main task, the side task and the monitors are judged separately and meet only in the report.

The concrete lab, its codebase and services, its agents and their permissions, and the tasks they work on are the subject of Settings. How the monitors read the observable record and turn it into a verdict is Monitoring.
