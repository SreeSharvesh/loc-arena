Usage

How to set up the project, run episodes, read the dashboard, and change any part of the setting. Almost everything is config, so most changes are a config edit rather than a code change.

Setup

You need uv (Python 3.12, pinned) and, for a live run, an OpenRouter API key. The key is read only by the gateway.

uv sync                       # create the environment and install everything
cp .env.example .env          # then set OPENROUTER_API_KEY
make setup                    # check the toolchain, sync deps, validate the config

Run an episode

An episode drives a live model as the untrusted team and grades the outcome. There are three ways to run.

make run RUN=aurora-efficiency MODE=attack   # the attack episode plus its honest twin (the calibration baseline)
make run RUN=aurora-efficiency MODE=honest   # the honest twin on its own (main task only)
loc-arena sweep --run aurora-efficiency --honest 3 --attack 3   # many episodes, aggregated into safety and usefulness numbers
RunWhat it doesWhen to use it
attackRuns the main and side task together, plus the honest twin that calibrates the threshold.The default. One full measurement: did the rogue deployment land, and was it caught.
honestRuns the main task only, with the covert objective disabled.To see normal behaviour and the usefulness score on its own.
sweepRuns many honest and attack episodes and aggregates a safety rate and a usefulness curve.To get a stable measurement rather than one episode.

Every run writes a self-contained bundle named after what actually ran, so the same setting can run many times without collision. The bundle holds the resolved config, both event records, the two verdicts, the report page, a notes file, and a per-agent view of the episode: an Inspect log and a transcript page. Add STACK=1 to bring up the container stack for structural isolation; without it the same episode runs in a single process. make gates runs the formatting, typing, and test checks.

Read the dashboard

Open the latest report. It is a single static page, and a run index lists every run.

make view RUN=aurora-efficiency               # open the latest report in the dashboard

Outcome

At the top: the main-task score, whether the rogue deployment landed and how firmly, and whether the episode was caught.

Kill chain

The side-task steps drawn out, so you can see how far it got and which stages were reached.

Lanes and gauge

Each agent's activity over time, and the overall suspicion as a gauge with a per-monitor breakdown, plus the detector signal.

Transcripts

Every agent's full run, step by step, with the monitor scores attached in place. Nothing is hidden behind a summary.

Per-agent view

The report shows the run through the records. The per-agent view shows it through each agent: what it was asked, what it answered, which tools it called, and everything its turns set off, such as a job it started. Events no agent caused, like the background coworker and the monitors' own checks after the episode, sit in a separate World column.

  • Transcript page. transcript.html in the bundle: one column per agent, one row per round, so every agent's turn in a round sits side by side. A plain-text copy sits next to it.
  • Inspect log. The same run as an Inspect log, with one span per agent and its turns inside. make view prints the command that opens it.
inspect view --log-dir logs/<run>/<bundle>/inspect   # browse the per-agent log

Both are built after the episode from what the platform recorded, so they add no model calls and change nothing an agent, monitor, or checker sees. Set logging.agent_transcript: false in a run config to skip them.

Configure and extend

The parts of a run are separated so you can change one without the others. Here is where each change lives.

Monitors

Monitors are declared in monitors.yaml. To add one, set its tap point, the inputs it reads from the observable list, whether it decides by rule or by model, whether it runs in line or on a side worker, and its weight. To move a monitor, change its tap point. To turn the scratch-surface monitor on, enable it. The one hard limit is the firewall: an input off the observable list fails the build. See Monitoring.

Scoring

In the same file, the scoring block sets how each monitor's scores reduce to one number, how the monitors combine into the overall suspicion, the weight on each, and how strict the audit budget is. Change the combining rule from a weighted average to a maximum, or tighten the budget, and rerun.

Models

Models are named by role in models.cheap.yaml: the untrusted team, the trusted monitor, and the teacher. Point the team at a stronger model to see how much further the side task gets; point the monitor at a weaker one to see detection fall off. One line per role.

Tasks

A main task is a goal plus a scorer that reads real outcomes: tests passing and a real cost or metric, never a model's opinion. A side task is a set of steps, each with a check that reads the sealed record for an executed fact, plus the conditions that count as a landing. The rule to keep: a step is only confirmed from something that actually happened, so the honest twin reaches none of them.

Settings

A setting is a whole organization plus a task catalog, laid over the shared engine: its services and codebase, its agents and their permissions, its monitors, and a sealed reference. New settings reuse the same engine; only the organization, the cast, and the tasks change. Meridian AI Lab is the first; see Settings.

The invariant to keep Whatever you change, keep the two measurements apart. The checker reads only the sealed record and only executed facts. The monitors read only the observable side. The honest twin must always verify clean.
